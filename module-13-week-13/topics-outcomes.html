1. Databases as the Foundation of Data Analysis

Description

Introduces data analysis as the process of inspecting, cleaning, transforming and modelling data, and explains why relational databases and SQL sit at the heart of that work. Contrasts transactional (OLTP) and analytical (OLAP) use, surveys business domains that rely on database analysis, and walks through the six-stage pipeline from source data to delivered report.

Subtopics

  • What Data Analysis Is — Data analysis is the process of inspecting, cleaning, transforming and modelling data to discover useful information, draw conclusions and support decision making. In organisational settings, that process almost always begins with data held in a relational database.
  • Why Databases Sit at the Heart of Analysis — Databases are the primary system of record for organisational data — they store it, structure it and make it queryable at scale. Even when analysis finishes in a visualisation tool, the extraction and preparation work starts with SQL.
  • Transactional (OLTP) Use of Databases — Transactional systems exist to record and process live business events as they happen. Their workload is made up of many short INSERT, UPDATE and SELECT statements running concurrently.
  • Analytical (OLAP) Use of Databases — Analytical use aggregates and summarises data to produce insight rather than to record events. Queries are complex SELECT statements scanning large row counts.
  • Business Domains That Rely on Database Analysis — Almost every sector stores operational data in databases and runs regular analyses against it. The domain changes the tables and metrics, but the query patterns stay remarkably consistent.
  • The Six-Stage Analysis Pipeline — Every analysis follows the same path from raw operational data to a delivered report. Treating it as a repeatable pipeline makes results consistent and auditable.

2. Types of Data Used in Analysis

Description

Explains the data classifications that determine which analytical operations are valid: quantitative versus qualitative, structured versus semi- and unstructured, and the three forms of time-series data. Introduces the dimensions-and-measures framing that drives the core GROUP BY query pattern and shows typical analytical column types in a sales fact table.

Subtopics

  • Why Data Type Classification Matters — Before analysing data you must understand what kind of data you are working with, because different data types support different analytical operations. Applying the wrong operation to a data type produces results that look valid but are meaningless.
  • Quantitative vs Qualitative Data — The first split is between numeric data that represents a measurable quantity and categorical data that represents labels or descriptions. Quantitative data supports arithmetic; qualitative data supports counting and grouping.
  • Structured, Semi-Structured, and Unstructured Data — Data also varies by how rigidly it is organised, which determines how much preparation is needed before SQL can analyse it. Structured data is query-ready; the other forms require extraction or external tooling.
  • Time-Series Data and Its Three Forms — A time series is a sequence of values recorded at regular time intervals, and most business metrics are time-series in nature — revenue by day, users by month, inventory by week. Time-series data appears in three recognisable shapes.
  • Dimensions and Measures — In analytical thinking, every column in a dataset is either a dimension or a measure. This framing is what guides how you construct GROUP BY queries.
  • The Core Analytical Query Pattern — The dimensions-and-measures framing resolves into one dominant SQL shape that produces the majority of business reports. Choose which dimension to slice by and which measure to aggregate.
  • Typical Analytical Columns in a Sales Fact Table — A sales fact table illustrates how these classifications appear together in a real schema. Columns are deliberately grouped into date/time dimensions, categorical dimensions, and numeric measures.

3. Preparing and Cleaning Data for Analysis

Description

Covers the data quality problems — NULLs, duplicates, inconsistent formats, wrong data types, outliers and out-of-range values — that invalidate analysis if left unaddressed. Provides SQL techniques for NULL handling with COALESCE, deduplication with ROW_NUMBER, category standardisation with CASE, date conversion, outlier detection via z-scores, and upfront data profiling.

Subtopics

  • Why Data Preparation Matters — Raw data from operational systems is rarely clean enough to analyse directly, and preparation typically consumes the majority of an analysis project. Skipping this step produces results that look authoritative but are misleading.
  • Common Data Quality Problems — Six recurring problems account for most of the data quality issues an analyst encounters. Recognising each pattern is the first step to choosing the right remedy.
  • Handling NULL Values with COALESCE — NULL means 'unknown', not zero, and different treatments of NULL produce genuinely different business answers. COALESCE lets you substitute a default so the aggregate reflects the population you intend.
  • Identifying and Removing Duplicates — Duplicate rows must be found and removed before any aggregation, or every total will be overstated. SQL offers a detection pattern and a deduplication pattern.
  • Standardising Categories and Converting Dates — Inconsistent category labels create phantom groups in GROUP BY, and dates stored as text block all time-based analysis. CASE expressions and date conversion functions fix both on the fly.
  • Detecting Outliers with Z-Scores — Outliers are extreme values that distort averages and can mask the real pattern in the data. A standard statistical test flags values that sit an unusual distance from the mean.
  • Data Profiling Before Analysis — Profiling means running a quick diagnostic query over the dataset before writing any analytical SQL. It prevents surprises that would otherwise invalidate your results.

4. Descriptive Analysis — Summarising What Happened

Description

Shows how aggregation compresses raw events into the summary numbers that underpin every dashboard and routine report. Builds a complete monthly sales summary, slices revenue by category with percentage-of-total window functions, and uses conditional counting with CASE WHEN to pivot statuses into columns.

Subtopics

  • What Descriptive Analysis Answers — Descriptive analysis answers the question "What happened?" by compressing large volumes of raw transactional events into a small set of meaningful summary numbers.
  • The Standard Monthly Summary Report — Most daily, weekly and monthly reports are built from a small, repeatable set of aggregation patterns applied to a date-based grouping.
  • Derived Metrics and Safe Division — Summary reports rarely stop at raw totals — most include at least one calculated ratio such as profit margin that puts the totals in context.
  • Slicing by Dimension — Category Breakdown — Once the period total is known, the next question is which part of the business drove it; this is answered by grouping on a categorical dimension instead of a date.
  • Percentage of Total with Window Functions — A share-of-total column turns raw category figures into proportions, showing how much of the whole each group represents without a second query or subquery.
  • Conditional Counting with CASE WHEN — Conditional aggregation pivots a column of status values into separate count columns in a single query, producing a compact cross-tab style report.

5. Trend and Time-Series Analysis

Description

Addresses whether a metric is improving or declining through period-over-period comparison. Demonstrates month-over-month and year-over-year change with LAG, cumulative running totals, and rolling moving averages, plus the seasonality, trend, spike and day-of-week patterns to watch for.

Subtopics

  • Why Trend Analysis Matters — Trend analysis answers the question: is this metric going up, down, or staying flat? It adds the context that turns a raw number into a story a decision-maker can act on.
  • Period-Over-Period Comparison with LAG() — The LAG() window function retrieves a value from a previous row, making it the core technique for month-over-month comparison. Aggregate to the period level first in a CTE, then apply LAG over that result.
  • Year-Over-Year Comparison — Year-over-year comparison measures each month against the same month one year earlier, which neutralises seasonal effects that distort month-over-month figures.
  • Running Totals (Cumulative Sum) — A running total accumulates values forward through time, commonly used to track year-to-date progress against a target.
  • Rolling (Moving) Averages — A moving average smooths out short-term volatility so the underlying direction of the metric becomes visible. A 7-day moving average is the standard choice for daily data.
  • Time-Series Patterns to Watch For — When reading a trend line, four recurring patterns explain most of what you see. Recognising which one is present stops you from misinterpreting normal behaviour as a problem.

6. Segmentation and Ranking Analysis

Description

Divides populations into meaningful sub-groups and orders entities by a measure to reveal where value is concentrated. Covers Top-N reporting, RANK and DENSE_RANK within groups, CASE-based customer value tiers, the 80/20 revenue pattern, and NTILE quartile or decile segmentation.

Subtopics

  • Purpose of Segmentation and Ranking — Segmentation divides a population into meaningful sub-groups, while ranking orders entities by a measure. Together they answer the analytical question "where should we focus?"
  • Top-N Analysis — Finding the top or bottom N records by a measure is one of the most frequently requested report types in business reporting.
  • Ranking Within Groups Using RANK and DENSE_RANK — Window ranking functions assign a position to each row within a partition, allowing you to rank entities inside each category rather than across the whole dataset.
  • Customer Value Segmentation with CASE — CASE expressions group customers into named value tiers based on thresholds of a measure such as lifetime spend.
  • The 80/20 Pattern in Business Data — In most business datasets, roughly 20% of customers, products or sales reps generate about 80% of the revenue. Segmentation makes this concentration visible and actionable.
  • Quartile and Decile Segmentation with NTILE — NTILE divides an ordered result set into a specified number of approximately equal-sized buckets, producing data-driven segments instead of fixed thresholds.

7. KPIs and Rate Metrics

Description

Defines key performance indicators as the normalised rate metrics organisations track against goals, rather than raw totals. Demonstrates computing conversion rate, average order value, return rate and revenue per visitor in SQL, the critical use of NULLIF to avoid division by zero, and a reference table of common business KPI formulas.

Subtopics

  • What a KPI Is — and Why Rates Beat Raw Totals — Key Performance Indicators (KPIs) are the specific metrics an organisation tracks to evaluate progress towards its goals. Most KPIs are rate metrics — ratios that normalise a measure against a base — rather than raw totals.
  • Reading a KPI Dashboard — KPI dashboards present a small set of headline numbers, each with a comparison against a prior period. The comparison is what turns a number into a story.
  • Computing Rate KPIs in SQL — Rate KPIs follow a consistent SQL shape: an aggregated numerator divided by an aggregated denominator, multiplied by 100.0 when a percentage is wanted. Several KPIs can be computed together in a single query over the same joined dataset.
  • NULLIF and the Division-by-Zero Problem — Any rate metric risks a denominator of zero — a day with no visitors, a category with no orders. NULLIF() is the standard defence.
  • Reference Library of Common Business KPIs — A small set of KPI formulas recurs across almost every business domain. Knowing the formula and its SQL pattern lets you build most rate metrics on demand.
  • Defining KPIs Consistently — The same KPI name can mean different things to different teams, so a documented definition matters as much as the SQL. Agreeing the numerator, the denominator and the filter conditions prevents conflicting numbers in meetings.

8. Cyclic Reporting and Analysis Patterns Reference

Description

Explains how daily, weekly, monthly, quarterly and annual reports are standardised and parameterised by date so one query serves any period, including stored procedures for scheduled execution and year-to-date comparisons. Concludes with a quick-reference table of core SQL analysis patterns, the descriptive-comparative-segmentation thinking framework, best practices for a reporting practice, and how SQL feeds visualisation tools.

Subtopics

  • What Cyclic Reports Are and Why They Are Standardised — Cyclic reports run on a fixed schedule — daily, weekly, monthly, quarterly, annually — and feed recurring business decisions. Because the same question is asked every period, the query should be written once and reused rather than rewritten each cycle.
  • Parameterising a Report Query by Date — A well-designed cyclic report declares date variables for the start and end of the period instead of hardcoding literal dates. The same query then serves any week, month or quarter without modification.
  • Typical Cyclic Report Types by Frequency — Different reporting frequencies serve different audiences and carry different metrics. Matching the frequency, metric set and audience is a key design decision.
  • Stored Procedures for Scheduled Execution — Wrapping a report query in a stored procedure allows a scheduler such as SQL Server Agent to run it automatically, with the procedure calculating its own dates when no parameters are supplied.
  • Year-to-Date and Same-Period-Last-Year Comparison — Year-to-date reporting accumulates the current year's performance and compares it against the same elapsed portion of the prior year. Without the elapsed-day restriction, the comparison would be unfair.
  • Quick Reference — Core SQL Analysis Patterns — A small set of SQL techniques covers the great majority of business analysis requests. Knowing which pattern answers which question speeds up report writing considerably.
  • The Analytical Thinking Framework — Business analysis questions generally fall into three layers: describing what happened, comparing it to prior periods, and segmenting to decide where to focus. Together they turn raw numbers into a narrative.
  • Best Practices for a Regular Reporting Practice — A sustainable reporting practice depends as much on discipline and process as on SQL syntax. These habits prevent the common failures that make recurring reports untrustworthy.
  • Feeding Visualisation Tools from SQL — The structured result sets produced by these queries are consumed directly by reporting and BI platforms. SQL performs the preparation and aggregation; the tool handles charts and formatting.
