Module 14 (Week 14) - NoSQL — Module Topics

NoSQL Fundamentals and Database Types

Introduces what NoSQL means, why it emerged, and the four main families — document, key-value, column-family, and graph stores — along with their typical use cases and leading products. Compares NoSQL and relational systems across data model, schema, relationships, scaling, and consistency.
  • What NoSQL Means and Why It Emerged — NoSQL stands for "Not Only SQL" — a broad category of database systems that store and retrieve data using models other than the traditional relational table. These systems emerged to address limitations of relational databases under specific modern workloads.
  • Document Stores — Document stores keep data as self-contained documents, typically in JSON or BSON format, grouped into collections. They are the most flexible and widely used NoSQL type.
  • Key-Value Stores — Key-value stores are the simplest NoSQL model: every item is stored as a key paired with an associated value. They deliver extremely fast performance for simple lookups.
  • Column-Family (Wide-Column) Stores — Column-family stores organise data into rows, but group columns into column families, allowing each row to have a different set of columns. They are engineered for enormous distributed write throughput.
  • Graph Databases — Graph databases store data as nodes representing entities and edges representing the relationships between them. Relationships are first-class citizens rather than derived at query time.
  • NoSQL vs Relational — Key Differences — Comparing a document store with a relational database highlights fundamental differences in data model, schema handling, relationships, scaling strategy, and consistency guarantees.
  • Choosing the Right Store and Polyglot Persistence — NoSQL is not a replacement for relational databases — it is an alternative optimised for different problems. The right choice depends on what the data looks like and how it must be accessed.

MongoDB Core Concepts: Documents, Collections, and BSON

Explains the MongoDB hierarchy of databases, collections, documents, and fields and how it maps to relational tables, rows, and keys. Covers BSON data types, embedded documents, array fields, and basic shell commands for connecting and selecting a database.
  • The MongoDB Storage Hierarchy — MongoDB organises data as BSON documents grouped into collections, which live inside a named database. This hierarchy maps loosely onto the relational model but relaxes many of its rules.
  • The _id Field and Document Identity — Every MongoDB document must have a unique _id field, which acts as its primary key. MongoDB generates one automatically if you do not supply it.
  • Anatomy of a MongoDB Document — Documents look like JSON objects but can contain nested objects and arrays, so an entire related data set can live inside a single document.
  • Schema Flexibility Across Documents — Collections do not enforce a fixed schema, so documents in the same collection may have different sets of fields. This is the defining difference from a relational table.
  • BSON Data Types — MongoDB stores data in BSON — Binary JSON — a binary superset of JSON that supports additional data types not available in plain JSON.
  • Connecting and Selecting a Database in mongosh — The MongoDB shell, mongosh, is the primary interactive tool for connecting to a server and working with databases and collections.

Creating and Reading Documents

Covers inserting documents with insertOne and insertMany and the schema flexibility that allows varying field sets. Covers querying with find and findOne, projections, comparison and logical operators, array and embedded-document queries, sorting, limiting, skipping, and counting.
  • insertOne — Adding a Single Document — The insertOne() method adds one document to a collection, creating the collection automatically if it does not yet exist. No CREATE TABLE statement or schema definition is required beforehand.
  • insertMany — Bulk Document Insertion — insertMany() accepts an array of documents and inserts them in a single operation, which is far more efficient than repeated single inserts.
  • Schema Flexibility on Insert — Documents in the same collection are not required to share the same fields, which is one of the defining characteristics of a document store.
  • find and findOne — Basic Queries — Reads use a filter document — a JSON object whose key-value pairs specify the conditions a document must match. An empty filter {} returns every document.
  • Projection — Controlling Returned Fields — The second argument to find() is a projection document that specifies which fields appear in the result, equivalent to choosing columns in a SQL SELECT list.
  • Comparison and Logical Operators — MongoDB query operators begin with a dollar sign and express conditions beyond simple equality, mirroring SQL comparison and boolean logic.
  • Array, Embedded Document, and Result-Shaping Queries — Documents often contain arrays and nested objects, and MongoDB provides dedicated syntax to query inside them as well as cursor methods to order and page results.

Updating and Deleting Documents

Explains update operators such as $set, $inc, $push, and $addToSet used with updateOne, updateMany, and upsert operations. Covers deleteOne, deleteMany, dropping collections, and the safety practices needed because deletions are permanent.
  • Update Operators: Describing What Changes — MongoDB updates do not replace a whole document by default; instead you supply update operators that describe precisely which fields should change. This lets you modify one field while leaving the rest of the document untouched.
  • Array Update Operators — Because MongoDB documents often contain arrays of values or sub-documents, dedicated operators exist for modifying array contents in place. These avoid having to read, edit, and rewrite the whole array from the application.
  • updateOne vs updateMany — MongoDB distinguishes between modifying a single matching document and modifying every document that matches a filter. Choosing the wrong one can silently change far more data than intended.
  • Upsert — Update or Insert — An upsert combines update and insert: if a matching document exists it is updated, and if none exists a new document is created from the filter and update values. It is enabled with the { upsert: true } option.
  • Deleting Documents with deleteOne and deleteMany — Deletion uses the same filter syntax as find(), with deleteOne removing the first match and deleteMany removing every match. Deletes in MongoDB are immediate and permanent unless performed inside an explicit transaction.
  • Dropping Collections and Databases — Beyond removing individual documents, MongoDB can discard an entire collection or database in a single command. These operations also remove indexes and metadata, so they are far more destructive than a delete.
  • Safety Practices for Destructive Operations — Because updates and deletes act on everything a filter matches, verification habits are essential. A small filter error can affect an entire collection in milliseconds.

The Aggregation Pipeline

Introduces multi-stage aggregation as MongoDB's answer to SQL GROUP BY, JOIN, and HAVING. Covers key stages including $match, $group, $project, $sort, $unwind, and $lookup through worked analytical examples.
  • What the Aggregation Pipeline Is — The aggregation pipeline processes documents through a sequence of stages, where each stage transforms the documents and passes the results to the next stage. It is MongoDB's answer to SQL's GROUP BY, JOIN, HAVING, and complex SELECT expressions.
  • Core Pipeline Stages and Their SQL Equivalents — Most analytical pipelines are built from a small set of commonly used stages that map closely onto familiar SQL clauses. Learning these equivalences makes the pipeline much easier to reason about.
  • $match and Pipeline Efficiency — $match filters the document stream using the same query syntax as find(). Placing it as early as possible is the single most important performance habit in aggregation.
  • $group and Aggregate Accumulators — $group collects documents sharing a common key and computes summary values across each group. The _id field defines the grouping key, and accumulator operators produce the aggregates.
  • Shaping Output with $project and $sort — After grouping, $project reshapes the result documents by renaming, computing, or hiding fields, and $sort orders the final output. Together they produce a clean, report-ready result set.
  • $unwind — Analysing Array Elements — $unwind expands an array field so that each element becomes its own document. This makes it possible to group and count individual items stored inside arrays.
  • $lookup — Joining Collections — $lookup performs the equivalent of a SQL LEFT JOIN by pulling matching documents from another collection into an array field. It is the main tool for querying referenced (non-embedded) data.

Data Modelling: Embedding vs Referencing

Examines the central MongoDB design decision between embedding related data inside a document and referencing it from a separate collection. Provides criteria such as access patterns, bounded growth, data sharing, and the 16MB document size limit.
  • Access Patterns Drive MongoDB Schema Design — The most important design decision in MongoDB is whether to embed related data inside a document or reference it from a separate collection. Unlike relational databases where normalisation rules drive schema design, MongoDB modelling is driven by how the data is actually accessed.
  • Embedding — Related Data Inside One Document — Embedding stores related data as nested sub-documents or arrays within the parent document. A customer document can carry its home and work addresses directly inside an addresses array.
  • Referencing — Linked Documents Across Collections — Referencing keeps related data in a separate collection and links it with a stored identifier, such as a customer_id field holding the customer's ObjectId. This mirrors the foreign-key approach used in relational databases.
  • Criteria for Choosing Embedding — Embedding is the right choice when related data behaves as part of the parent entity and stays small. Four criteria signal that embedding will perform well.
  • Criteria for Choosing Referencing — Referencing is preferable when the related data has an independent life cycle, grows without limit, or is shared. These conditions make embedding costly or impossible.
  • The 16MB Document Size Limit — MongoDB enforces a hard maximum of 16MB per BSON document, which acts as a practical ceiling on how much data can be embedded. Any array that can grow without bound risks hitting this limit.
  • Trade-offs and Practical Guidance — Neither approach is universally correct; each trades read simplicity against update cost and flexibility. Many real schemas combine both patterns within the same application.

Indexing and Query Performance

Covers creating single-field, compound, unique, text, and TTL indexes and how they prevent full collection scans. Explains using explain() to distinguish COLLSCAN from IXSCAN and evaluate query efficiency.
  • Why Indexes Matter in MongoDB — MongoDB indexes use the same B-tree principle as relational indexes, allowing the engine to locate matching documents without reading the whole collection. Without an index, every query performs a collection scan.
  • Single-Field and Compound Indexes — The most common indexes target one field or a combination of fields that queries filter and sort on. The value 1 means ascending order and -1 means descending.
  • Unique Indexes for Data Integrity — A unique index enforces that no two documents share the same value for the indexed field, serving the same role as a UNIQUE constraint in SQL.
  • Text and TTL Indexes — MongoDB offers specialised index types for full-text search and for automatic expiry of time-limited data.
  • Managing Indexes — Indexes should be reviewed over time so that unused or redundant ones do not consume storage and slow writes.
  • Using explain() to Evaluate Query Performance — The explain() method reveals how MongoDB executed a query, including whether an index was used and how many documents were examined.

Choosing Between NoSQL and Relational Databases

Provides side-by-side SQL and MongoDB syntax comparisons for create, read, update, and aggregate operations. Presents decision criteria, limitations of NoSQL, and the polyglot persistence approach of combining multiple database types in one architecture.
  • Syntax Comparison: Create and Read Operations — The same data operations look different but map closely between SQL and MongoDB. Understanding the translation helps SQL-trained developers become productive in MongoDB quickly.
  • Syntax Comparison: Update and Aggregate Operations — Updates and analytics also have direct equivalents, though MongoDB uses explicit update operators and a staged pipeline instead of single declarative statements.
  • When to Choose MongoDB (Document Store) — MongoDB is the stronger choice when data structure varies, evolves quickly, or is naturally nested. Its strengths align with rapid development and large-scale, write-heavy workloads.
  • When to Choose a Relational Database — Relational systems such as SQL Server or PostgreSQL remain the better choice for structured, highly relational, transaction-critical data. Their constraints and query expressiveness are features, not limitations.
  • Decision Criteria Summary — A side-by-side factor comparison helps structure the choice rather than relying on preference or hype. Evaluate schema, data shape, relationships, transactions, scale, query complexity, and development speed.
  • Limitations and Trade-offs of NoSQL — NoSQL gains flexibility and scalability by giving something up elsewhere. Documenting these limitations is essential when justifying a database choice.
  • Polyglot Persistence: Using Multiple Databases Together — Large-scale applications rarely pick one database for everything. Polyglot persistence means selecting the best-fit database for each distinct workload within a single architecture.
