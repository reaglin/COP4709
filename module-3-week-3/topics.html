Module 3 (Week 3) — Module Topics

Foreign Keys and Identity Columns Fundamentals

Explains the challenge of inserting data across tables linked by foreign keys and how SQL Server identity columns automatically generate unique primary key values. Covers IDENTITY(seed, increment) syntax, custom seeds, and why identity gaps occur.
  • The Foreign Key Insert Challenge — Relational databases link tables through foreign keys, which creates an ordering problem when inserting new data. A parent row must exist before any child row that references it can be inserted.
  • Why Use Identity Columns — An identity column tells SQL Server to generate a unique numeric value for each new row automatically. This removes the burden of key generation from application code.
  • IDENTITY(seed, increment) Syntax — The IDENTITY property is declared on a single numeric column and takes two arguments: the seed (starting value) and the increment (step size). It is typically paired with PRIMARY KEY.
  • Custom Seeds and Increments — Seed and increment values can be customized to meet business or formatting requirements. This is useful when IDs must start at a particular number or follow a stepped pattern.
  • Identity Gaps Are Normal — Identity values are consumed when generated and are never reused, so the sequence can contain gaps. This is expected behavior, not a defect.
  • Identity Columns in the Example Schema — The e-commerce schema uses identity columns on every primary key and foreign key constraints to link the tables. This setup illustrates why retrieving generated identity values matters.

Retrieving Generated Identity Values

Compares SCOPE_IDENTITY(), @@IDENTITY, IDENT_CURRENT(), and the OUTPUT clause for capturing newly generated keys. Highlights scope, trigger safety, and concurrency implications so learners choose the correct method for each situation.
  • Why You Need Identity Retrieval Functions — Identity columns let SQL Server automatically generate unique sequential keys, but the generated value is not returned to you by the INSERT statement itself. To use a new key as a foreign key in a child table, you must explicitly capture it.
  • SCOPE_IDENTITY() — The Recommended Default — SCOPE_IDENTITY() returns the last identity value generated within the current scope — the current stored procedure, trigger, function, or batch. This makes it the safest general-purpose choice for single-row inserts.
  • @@IDENTITY — Use With Caution — @@IDENTITY returns the last identity value generated anywhere in the current session, regardless of scope. This makes it vulnerable to returning a value produced by a trigger rather than by your own INSERT.
  • IDENT_CURRENT() — Table-Specific and Risky — IDENT_CURRENT('TableName') returns the last identity value generated for a specific table across all sessions and scopes. Because it ignores who generated the value, it is unsafe for retrieving a key you just inserted.
  • The OUTPUT Clause — Most Flexible — The OUTPUT clause captures values directly from the rows affected by an INSERT, using the inserted pseudo-table. It is the only reliable option when a single statement inserts multiple rows.
  • Choosing the Right Method — Each method differs in scope, trigger safety, and concurrency safety, so the correct choice depends on whether you are inserting one row or many and whether triggers exist on the table.

Designing the Schema and Dependency Order

Walks through a complete e-commerce schema (Customers, Products, Orders, OrderItems, Addresses) with its foreign key constraints. Introduces dependency-level thinking to determine the correct order of inserts across related tables.
  • The E-Commerce Schema at a Glance — The working example for this module is a five-table e-commerce schema: Customers, Products, Orders, OrderItems, and Addresses. Each table uses an INT IDENTITY(1,1) primary key so SQL Server generates surrogate keys automatically.
  • Foreign Key Constraints in the Schema — Four named foreign key constraints wire the tables together and enforce referential integrity at the database level. Naming constraints explicitly makes errors and maintenance far easier to interpret.
  • Dependency-Level Thinking — Grouping tables into dependency levels turns an abstract diagram into a concrete insert plan. A table's level is one higher than the highest level of any table it references.
  • Deriving the Correct Insert Order — Rows must always be inserted parent-first, moving from the lowest dependency level upward. Inserting a child before its parent raises a foreign key violation and aborts the statement.
  • Validating Parent Rows Before Inserting — Even with the right ordering, a child insert can fail if the supplied parent key does not exist. Explicit validation produces clearer, more actionable errors than raw constraint violations.
  • Why Identity Columns Shape the Design — Because every primary key in this schema is an identity column, child values cannot be known until the parent row is actually inserted. This is precisely what makes dependency order and key retrieval inseparable.

Building INSERT Stored Procedures

Demonstrates progressively complex insert procedures: a simple insert returning an identity value, a one-level foreign key insert with validation, and a multi-level insert that resolves related keys. Includes OUTPUT parameters and usage examples for calling each procedure.
  • Procedure Structure and the OUTPUT Parameter Pattern — Every insert procedure in this module follows the same skeleton: input parameters, SET NOCOUNT ON, validation, the INSERT, capture of the identity value, and a return code. OUTPUT parameters are the standard way to hand the newly generated key back to the caller.
  • Simple Insert Returning an Identity Value — The simplest case inserts into a table with no foreign key dependencies and returns the generated primary key. usp_InsertCustomer demonstrates this pattern against the Customers table.
  • One-Level Foreign Key Insert with Validation — When the target table references a parent, the procedure must confirm the parent row exists before inserting. usp_InsertOrder validates the customer, then creates the order and returns the new OrderID.
  • Multi-Level Insert Resolving Related Keys — At the deepest level a row may depend on two different parents and may need to look up data from one of them. usp_InsertOrderItem validates the Order, validates the Product, and pulls the current UnitPrice from Products.
  • Find-or-Create Logic for Lookup Parents — A common variation inserts the parent only when it does not already exist, reusing the existing key otherwise. The Music Database sp_InsertSong procedure illustrates this find-or-create pattern across Artists, Albums and Songs.
  • Chaining the Procedures Together — Because each procedure returns its generated key through an OUTPUT parameter, the three levels can be called in sequence to build a complete order from scratch.

Transaction Management for Multi-Table Inserts

Shows how to wrap related inserts in explicit transactions with TRY...CATCH, XACT_ABORT, and @@TRANCOUNT checks so that all operations succeed or fail together. Covers nested transaction handling and transaction scope best practices.
  • Why Transactions Matter for Related Inserts — When a single logical operation spans several tables connected by foreign keys, partial success leaves the database in an inconsistent state. Explicit transactions guarantee that every insert in the sequence either commits together or is undone together.
  • The BEGIN TRY / BEGIN TRANSACTION Pattern — The standard T-SQL structure wraps BEGIN TRANSACTION and all inserts inside a BEGIN TRY block, with COMMIT TRANSACTION as the last statement before END TRY. The matching BEGIN CATCH block performs the rollback and error reporting.
  • Checking @@TRANCOUNT Before ROLLBACK — @@TRANCOUNT reports how many transactions are currently open on the connection. Testing it before issuing ROLLBACK prevents a secondary error when no transaction is actually active.
  • Using SET XACT_ABORT ON — SET XACT_ABORT ON instructs SQL Server to automatically terminate and roll back the entire transaction when a run-time error occurs. It is a safety net for errors that would otherwise leave a transaction open.
  • Nested Transaction Handling — A stored procedure may be called from another procedure that already started a transaction. The procedure should only begin and commit a transaction if it is the one that opened it.
  • Transaction Scope Best Practices — Good transaction design keeps the protected region narrow, predictable, and well tested. These guidelines apply to every multi-table insert procedure you write.

Error Handling, Validation, and Logging

Presents a comprehensive validation and error-handling pattern using RAISERROR, THROW, return codes, and OUTPUT error messages. Includes building an ErrorLog table and a reusable logging procedure for diagnostics.
  • Validate Inputs Before Touching Data — Defensive stored procedures check every assumption about foreign keys and business rules before any INSERT occurs. Validation up front avoids wasted work and constraint violations deep inside a transaction.
  • Raising Errors with RAISERROR and THROW — T-SQL offers two ways to signal failure: RAISERROR, which supports formatted messages and explicit severity/state, and THROW, which re-raises the original error intact.
  • TRY...CATCH With Transaction-Safe Rollback — Every procedure that performs related inserts should wrap its work in BEGIN TRY / BEGIN CATCH and guard the rollback with a transaction count check.
  • Return Codes and OUTPUT Error Messages — A stored procedure can communicate outcome two ways at once: a numeric RETURN code for status and OUTPUT parameters for identity values and human-readable error text.
  • Building an ErrorLog Table — Persisting error details to a dedicated table turns transient failures into a searchable diagnostic history.
  • A Reusable usp_LogError Procedure — Centralizing the logging INSERT in one procedure keeps CATCH blocks short and guarantees consistent diagnostics across the whole database.
  • Error Handling Standards and Pitfalls — Consistent conventions make error handling predictable for every developer and every calling application.

Advanced Techniques: Batch Inserts and Table-Valued Parameters

Covers creating user-defined table types and passing multiple rows into a procedure with READONLY table-valued parameters. Also shows the OUTPUT clause for capturing multiple inserted rows and composing complete orders in a single call.
  • Why Table-Valued Parameters? — Table-valued parameters (TVPs) let you pass multiple rows of data into a stored procedure in a single call, making them ideal for batch inserts across foreign key relationships.
  • Creating User-Defined Table Types — A TVP must be based on a user-defined table type created with CREATE TYPE ... AS TABLE. The type defines the columns and data types of the rows you intend to pass.
  • Declaring READONLY TVP Parameters — Inside a stored procedure, a table-valued parameter is declared with the table type name followed by the READONLY keyword, which is mandatory for TVPs.
  • Populating and Calling with a TVP — Callers declare a variable of the table type, insert rows into it, then pass it as a parameter on the EXEC statement.
  • Set-Based Validation and Insertion Inside the Procedure — Because a TVP behaves like a table, validation and insertion can be done with set-based statements instead of row-by-row loops.
  • Capturing Multiple Inserted Rows with the OUTPUT Clause — When a single INSERT creates many rows, SCOPE_IDENTITY() returns only the last value; the OUTPUT clause captures every generated key and column instead.
  • Composing a Complete Order in a Single Call — Advanced procedures combine TVPs, OUTPUT parameters, and transactions to create a customer, address, order, and all line items in one atomic call.

Evaluating Approaches and Professional Best Practices

Weighs stored procedures against ORM (Entity Framework), ADO.NET, and hybrid approaches across performance, maintainability, testability, and portability. Concludes with naming, performance, security, documentation, testing standards, and common pitfalls to avoid.
  • Strengths and Trade-offs of the Stored Procedure Approach — Stored procedures centralize multi-table insert logic inside the database, but that power comes with costs that must be weighed before standardizing on them.
  • Deciding When a Stored Procedure Is the Right Tool — Not every data operation belongs in a stored procedure; the decision depends on complexity, volume, and how often the rules change.
  • Alternative 1: ORM-Based Inserts with Entity Framework — Entity Framework can manage the same parent-child insert sequence in C#, using an explicit transaction and successive SaveChanges() calls to obtain generated keys.
  • Alternative 2: Application-Level Logic with ADO.NET — Raw ADO.NET gives fine-grained control by issuing parameterized INSERT statements that use the OUTPUT clause to return generated identity values.
  • Alternative 3: The Hybrid Approach and Comparison Matrix — Many production systems combine approaches: an ORM handles simple CRUD while stored procedures handle complex, high-value transactions.
  • Professional Standards: Naming, Performance, and Security — Consistent conventions and defensive coding habits make procedures predictable, fast, and safe to expose to applications.
  • Documentation, Testing, and Common Pitfalls — A professional procedure ships with a header comment block, a repeatable test plan, and deliberate avoidance of well-known mistakes.
