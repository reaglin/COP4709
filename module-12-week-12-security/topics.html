Module 12 (Week 12) - Security — Module Topics

Database Security Threat Landscape

Examines why databases are high-value targets and introduces the defence-in-depth model spanning network, OS, authentication, authorization, data, audit, and application layers. Covers the most common breach sources and the regulatory frameworks (PCI DSS, HIPAA, GDPR, SOX, FERPA) that mandate database controls.
  • Why Databases Are High-Value Targets — Databases concentrate an organization's most sensitive and regulated assets in one place, making them the prime objective of most serious attacks. A single successful breach can trigger consequences far beyond the IT department.
  • Defence in Depth: The Seven Security Layers — Effective database security requires protection at every layer so that an attacker who penetrates one layer is still stopped by the next. Seven distinct layers each protect a different aspect of the environment.
  • Common Sources of Database Breaches — Most real-world database compromises trace back to a small number of recurring attack sources. Recognising these categories helps prioritise defensive effort.
  • Regulatory Frameworks Mandating Database Controls — Several regulatory frameworks impose specific, auditable database security requirements. Non-compliance carries financial penalties independent of any actual breach.
  • Translating the Threat Landscape into Priorities — Understanding the layers and threat sources allows a hardening effort to be sequenced by risk reduction rather than convenience. Early actions should close the largest and most exploited gaps first.

Authentication, Authorization & Least Privilege

Covers verifying identity and controlling what authenticated users can do, including strong password policies, Windows/AD authentication, and role-based GRANT/DENY design. Explores least-privilege patterns, Row-Level Security, and Dynamic Data Masking for protecting sensitive columns.
  • Authentication vs. Authorization — Authentication and authorization are two distinct layers of the defence-in-depth model, and failing either creates a critical security gap. Authentication answers "Who are you?" while authorization answers "What can you do?"
  • Strong Login and Password Policy in SQL Server — SQL Server logins should never be created with weak, guessable passwords. Password policy options allow SQL Server to enforce Windows-level complexity, expiration, and forced change rules.
  • Windows / Active Directory Authentication — For internal systems, Windows or Active Directory authentication is preferred over SQL authentication because no password is stored in SQL Server at all. Identity is established through Kerberos or NTLM at the domain level.
  • The Principle of Least Privilege — Every login, application account, and user should have only the minimum permissions required to perform their function — nothing more. Over-privileged accounts are among the most exploited attack surfaces in database environments.
  • Role-Based GRANT and DENY Design — Permissions should be granted to roles rather than to individual users, so access is consistent, reviewable, and easy to revoke. DENY can then explicitly block dangerous operations even when a higher role would otherwise inherit them.
  • Row-Level Security (RLS) — Row-Level Security restricts which rows a user can see within a table, automatically and transparently. The same query returns only one region's orders to a sales rep but all orders to a manager.
  • Dynamic Data Masking for Sensitive Columns — Dynamic Data Masking hides sensitive column values from unauthorized users at query time without changing the stored data. It lets support and reporting staff work with records without ever seeing raw PII.

Encryption of Data at Rest and in Transit

Explains Transparent Data Encryption, column-level and Always Encrypted protection, TLS-enforced connections, and secure password hashing. Emphasizes certificate backup, key management, and why encryption is the last line of defence when other controls fail.
  • Why Encryption Is the Last Line of Defence — Encryption protects data even when every other control has failed. If an attacker steals a database file, a backup, or intercepts network traffic, encryption ensures they obtain only unintelligible ciphertext instead of readable records.
  • Transparent Data Encryption (TDE) — TDE encrypts the entire database at the file level — data files, log files, and backups — without requiring any application or query changes. It is the primary defence against theft of physical media or backup files.
  • Certificate Backup and Key Management — The TDE certificate is the single point of failure for an encrypted database. If it is lost, the database cannot be decrypted by anyone — including its legitimate owner.
  • Column-Level Encryption and Always Encrypted — For highly sensitive fields such as SSNs, payment card numbers, and healthcare identifiers, column-level encryption gives finer control than TDE by encrypting only specific columns under separate keys.
  • Encrypting Connections with TLS — Unencrypted database connections transmit credentials and query results in plaintext, exposing them to interception and man-in-the-middle attacks. Forcing TLS ensures all client sessions are encrypted in transit.
  • Secure Password Hashing — Never Store Plaintext — Application passwords must never be stored in plaintext or with reversible encryption, as a single database breach would expose every user credential instantly.

Auditing & Activity Monitoring

Shows how to configure SQL Server Audit, database audit specifications, and login auditing to create an immutable record of access and changes. Covers monitoring for suspicious sessions, failed logins, and anomalous hosts for both detection and compliance.
  • Why Auditing Matters: Detection and Forensics — Auditing creates an immutable record of who accessed what data, when, and from where. It serves both real-time detection of suspicious activity and after-the-fact reconstruction of an incident.
  • Creating a SQL Server Audit (Where Logs Go) — The server audit object defines the destination and behaviour of audit output. It is created at the server level and must be explicitly turned on.
  • Database Audit Specifications (What to Capture) — A database audit specification attaches to a server audit and defines exactly which actions and objects are recorded. This is where you scope auditing to sensitive tables and security-relevant events.
  • Querying and Protecting the Audit Log — Audit files are read with sys.fn_get_audit_file, which returns a structured event stream you can filter and sort. Protecting those files is as important as generating them.
  • Monitoring for Suspicious Sessions and Anomalous Hosts — Dynamic management views let you inspect live activity for signs of abuse, blocking, or connections from unexpected sources. These checks complement persistent audit logs with real-time visibility.
  • Login Auditing and Failed-Login Alerting — Login auditing records authentication attempts, which is the primary signal for brute force and credential stuffing attacks. SQL Server can capture successful logins, failed logins, or both.
  • Building an Alerting and Review Routine — Audit data only delivers value when someone or something acts on it. Define the specific conditions that trigger an alert and the cadence for human review.

Each attack is paired with concrete defences such as parameterized queries and surface area reduction.

Database Forensics After an Incident

Walks through the forensic principles of preservation, chain of custody, and evidence-based reconstruction. Covers capturing volatile session state, mining the transaction log and audit files, identifying exfiltrated data, and hunting for attacker persistence mechanisms.
  • The Three Forensic Principles — Database forensics is the process of collecting, preserving, and analyzing database evidence after a suspected security incident. The investigation must answer what happened, who did it, when it happened, and what data was affected.
  • Step 1 — Capture Volatile Session State — Active session data is the most perishable evidence in a database incident and is lost the moment a connection drops or the service restarts. Capturing it should be the very first action taken on discovery.
  • Step 2 — Mining the Transaction Log — The SQL Server transaction log records every modification made to the database, making it a powerful source for reconstructing exactly what data changed. The undocumented fn_dblog function, or third-party tools such as ApexSQL Log, can read it.
  • Step 3 — Reconstructing the Timeline from Audit Logs — SQL Server Audit files provide a persistent, file-based record that combines login events, DDL, and DML into a chronological narrative of the incident.
  • Step 4 — Identifying Accessed and Exfiltrated Data — Determining scope requires identifying which sensitive tables were read and how much data left the environment — a critical input to breach notification obligations.
  • Step 5 — Hunting for Attacker Persistence — Attackers routinely leave backdoors so they can return after the initial intrusion is remediated. Eradication is incomplete until these persistence mechanisms are found and removed.
  • Evidence Sources and Their Volatility — Each forensic source offers different visibility and survives for a different length of time, so collection must be prioritized by volatility — most perishable first.

Network & Infrastructure Hardening

Addresses network isolation, firewall restriction of SQL Server ports, disabling the Browser service, and surface area reduction of dangerous features. Includes service account hardening with dedicated least-privilege or managed service accounts.
  • Network Isolation — Databases Must Never Be Public-Facing — A database server should never be reachable directly from the public internet. It belongs in a private network segment that only application servers can reach.
  • Firewall Rules and SQL Server Port Restriction — Operating-system firewall rules restrict which hosts may reach SQL Server's listening ports. This is configured outside T-SQL but is essential security configuration.
  • Disabling the Browser Service and Changing Default Ports — The SQL Server Browser service advertises instances to the network and is unnecessary on single-instance servers. Changing the default port reduces hits from automated scanners.
  • Surface Area Reduction — Disabling Dangerous Features — Every enabled feature expands the attack surface. Features that the application does not use should be turned off and verified.
  • Service Account Hardening — The account that SQL Server runs under determines what an attacker inherits if the engine is compromised. It must be dedicated and least-privilege.
  • Patch Management and Host Hardening — Known CVEs in the database engine and host operating system are exploited because patches were not applied. Patch currency is part of infrastructure hardening.

Security Hardening Checklist & Applied Practice

Consolidates authentication, authorization, encryption, network, auditing, application, and backup controls into a systematic audit checklist with prioritized remediation order. Connects the checklist to the hands-on hacker/defender SQL injection report and discussion on the greatest database security risk.
  • Using the Hardening Checklist as a Systematic Audit Tool — The complete hardening checklist consolidates every security layer into a single, repeatable audit instrument. Each unchecked item represents a live attack surface rather than a theoretical gap.
  • Authentication, Authorization and Encryption Checks — The first three checklist domains govern who connects, what they can do, and whether data is readable if stolen. These controls address the identity and data-protection layers.
  • Network, Surface Area and Auditing Checks — These domains reduce the reachable attack surface and ensure that any activity is recorded. A database that cannot be reached and whose dangerous features are disabled is dramatically harder to exploit.
  • Application-Level and Backup Security Checks — Application code and backup files are the two places where strong database configuration is most often undone. Both domains carry ⚠️ critical items.
  • Prioritised Remediation Order — When hardening a database from scratch, order matters — some controls remove entire classes of risk immediately while others take longer to implement. The source gives a seven-step prioritisation sequence.
  • Applied Practice: The Hacker/Defender SQL Injection Report — The assignment applies the checklist by requiring a two-part report: planning a SQL injection attack, then defending against it. The attacker half is worth 40% and the defence half 60%, reflecting the emphasis on hardening.
  • Discussion: Identifying the Greatest Database Security Risk — The graded discussion asks you to name the single biggest risk to database security and the best practices that alleviate it. This forces you to prioritise rather than list every control.
