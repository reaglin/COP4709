CREATE PROCEDURE [dbo].[performTransaction]
(
  @FromAccountID INT,
  @ToAccountID INT, 
  @Amount FLOAT
)
AS
BEGIN
-- Check to see if accounts exist
DECLARE @FromAccountTest INT
SELECT @FromAccountTest = (SELECT Count(*) 
  FROM Accounts
  WHERE AccountID = @FromAccountID)
IF @FromAccountTest <> 1 
BEGIN
 RAISERROR('From Account Does Not Exist', 10, 1)
END
DECLARE @ToAccountTest INT
SELECT @ToAccountTest = (SELECT Count(*) 
  FROM Accounts
  WHERE AccountID = @ToAccountID)
IF @FromAccountTest <> 1 
BEGIN
 RAISERROR('To Account Does Not Exist', 10, 2)
END
-- At this point we can log the transaction
DECLARE @TransactionID INT 
EXEC @TransactionID = LogTransactionAttempt @FromAccountID, @ToAccountID, @Amount 
-- Check to see if sufficient balance
DECLARE @FromAccountBalance  FLOAT
SELECT @FromAccountBalance = (SELECT Balance
    FROM Accounts 
    WHERE AccountID = @FromAccountID)

IF (@FromAccountBalance < @Amount)     
BEGIN
  RAISERROR('Insufficient Balance', 10, 3)
END
-- Now we can start the transaction
BEGIN TRANSACTION 
UPDATE Accounts
 SET Balance = Balance - @Amount
 WHERE AccountID = @FromAccountID

IF (@@ERROR <> 0)
   BEGIN
    ROLLBACK TRANSACTION   /* if errors - rollback transaction */
    RETURN 
   END
UPDATE Accounts
SET Balance = Balance + @Amount
 WHERE AccountID = @ToAccountID
IF (@@ERROR <> 0)
   BEGIN
    ROLLBACK TRANSACTION   /* if errors - rollback transaction */
    RETURN 
   END

UPDATE TransactionLog
  SET Successful = 1
  WHERE TransactionID = @TransactionID

IF (@@ERROR <> 0)
   BEGIN
    ROLLBACK TRANSACTION   /* if errors - rollback transaction */
    RETURN 
   END
-- Transaction
COMMIT TRANSACTION
END -- Procedure
 
CREATE PROCEDURE [dbo].[LogTransactionAttempt]
(
  @FromAccountID INT,
  @ToAccountID INT, 
  @Amount FLOAT
)
 AS
 BEGIN
  INSERT INTO TransactionLog
  (
    FromAccountID,
    ToAccountID,
    Amount, 
    TransactionDate
  )
  VALUES 
  (
    @FromAccountID,
    @ToAccountID,
    @Amount,
    GETDATE()
  )
  RETURN @@IDENTITY
 END

ACID Properties

ACID is an acronym that represents the four fundamental properties that guarantee reliable transaction processing in database systems. These properties are essential for maintaining data integrity and consistency, especially in situations with concurrent access or potential system failures.

  • Atomicity: This property ensures that a transaction is treated as a single, indivisible unit of work. Either all changes within the transaction are made, or none are. There's no partial completion.

    • Example: In a bank transfer, both debiting the source account and crediting the destination account must happen together. If one fails, the entire transaction is rolled back.

  • Consistency: A transaction must maintain the database's integrity constraints. It transforms the database from one valid state to another.

    • Example: If a rule states that account balances cannot go below zero, the transaction system must prevent a withdrawal that would violate this rule.

  • Isolation: Transactions should operate independently of each other. Concurrent transactions should not interfere with each other's execution or results.

    • Example: If two users try to book the last seat on a flight simultaneously, the system must ensure that only one booking is successful.

  • Durability: Once a transaction is committed, the changes are permanent and survive even system failures (e.g., power outages, crashes).

    • Example: After a successful purchase, the record of that purchase remains in the database even if the server crashes immediately afterward.

Discussion of Importance

  • Data Integrity: ACID properties are crucial for ensuring the accuracy and reliability of data. They prevent data corruption and inconsistencies that can arise from partial updates or concurrent access.

  • Business Criticality: In many applications (e.g., finance, e-commerce, healthcare), data integrity is paramount. ACID transactions provide the necessary guarantees for these critical systems.

  • Simplified Development: Developers can rely on ACID properties to simplify application logic. They don't need to implement complex error handling or concurrency control mechanisms themselves.

  • System Reliability: ACID properties enhance the overall reliability of database systems, making them more resilient to failures and unexpected events.

Implementation Considerations

  • Performance Trade-offs: Achieving full ACID compliance can sometimes impact performance. Database systems often offer different isolation levels that allow for trade-offs between consistency and concurrency.

  • Distributed Systems: Implementing ACID properties in distributed database systems is more complex due to the challenges of coordinating transactions across multiple nodes.

In Summary

ACID properties are fundamental to reliable transaction processing in database systems. They ensure data integrity, consistency, and durability, which are essential for many critical applications. While there can be performance trade-offs, the benefits of ACID compliance generally outweigh the costs, especially in systems where data accuracy is paramount.

Implementing ACID

Let's explore how databases implement the ACID properties. It's a complex area, and the specific implementations vary between database systems (e.g., MySQL, PostgreSQL, Oracle, SQL Server, MongoDB), but the underlying principles are similar.1

1. Atomicity

  • Write-Ahead Logging (WAL): Before any changes are made to the actual data files, they are first written to a log file.2 This log is durable (usually on disk). This ensures that even if the system crashes during a transaction, the database can use the log to either complete the transaction or roll it back.3
  • Transactions Logs: Databases maintain logs of all operations within a transaction.4 These logs contain enough information to undo the changes if the transaction needs to be aborted.
  • Rollback: If a transaction fails or is aborted, the database uses the transaction log to undo any changes that were made. It restores the database to the state it was in before the transaction began.5

2. Consistency

  • Constraints: Databases define rules (constraints) about the data, such as data types, uniqueness, and referential integrity (e.g., foreign keys).6 The database system enforces these constraints. A transaction that violates a constraint is not allowed to commit.7
  • Triggers: Triggers are pieces of code that are automatically executed when certain events occur in the database (e.g., insert, update, delete).8 Triggers can be used to enforce complex consistency rules.9
  • Data Validation: Before committing a transaction, the database system validates the changes to ensure they adhere to all defined rules and constraints.

3. Isolation

  • Concurrency Control: Databases use various techniques to manage concurrent transactions, preventing them from interfering with each other.10 Common methods include:
    • Locking: Transactions can acquire locks on data items to prevent other transactions from accessing or modifying them.11 Different types of locks (e.g., shared locks, exclusive locks) provide varying levels of isolation.12
    • Multi-Version Concurrency Control (MVCC): MVCC allows each transaction to see a snapshot of the database at a particular point in time.13 This avoids many locking scenarios and improves concurrency. Each row has version information. A transaction reads the version of the data that was current when the transaction began.14
    • Optimistic Concurrency Control: Transactions proceed without acquiring locks.15 Before committing, the database checks if any conflicts have occurred. If there are conflicts, the transaction is rolled back.
  • Isolation Levels: SQL defines different isolation levels, which offer varying degrees of protection against concurrency problems (e.g., read uncommitted, read committed, repeatable read, serializable).16 Higher isolation levels provide more protection but can reduce concurrency.17

4. Durability

  • Write-Ahead Logging (WAL): As mentioned earlier, WAL is crucial for durability.18 Changes are written to the log first, ensuring that they are persisted even if the system crashes before the data files are updated.19
  • Data Replication: Many databases support data replication, where data is copied to multiple servers.20 This provides redundancy and ensures that data is not lost even if one server fails.
  • Backup and Recovery: Databases provide mechanisms for backing up data.21 These backups can be used to restore the database to a previous state in the event of data loss.22 Recovery procedures use the WAL to replay changes since the last backup.23

Example: A Simplified Bank Transfer

Let's imagine a bank transfer from account A to account B.

  1. Atomicity: The transfer involves two operations: debiting A and crediting B. The database ensures that either both operations happen, or neither does.24 If the system crashes halfway through, the transaction log will be used to roll back the debit from A.
  2. Consistency: The database has a constraint that account balances cannot be negative. If the debit from A would violate this constraint, the transaction is aborted, and B is not credited.
  3. Isolation: If two transfers try to debit A simultaneously, the database's concurrency control mechanism (e.g., locking) ensures that these operations are performed in a way that prevents a "race condition" (where the final balance of A is incorrect). MVCC would allow the two transactions to read A's balance concurrently, but only one would be able to successfully update it.
  4. Durability: Once the transfer is committed, the changes to the balances of A and B are written to the transaction log and eventually to the data files. These changes are permanent, even if the system crashes immediately afterward.

It's important to understand that the specific implementation details can be quite complex and vary significantly between database systems. However, the core principles of ACID remain the same, providing a foundation for reliable data management.
