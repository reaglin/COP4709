Module 2 (Week 2) - ETL and Query — Module Topics

Importing XML Data from Data.gov into SQL Server

Walks through locating and downloading an XML dataset from Data.gov and moving it into SQL Server, using Excel and XML as intermediate steps in the import workflow. Assumes working familiarity with both SQL Server and Excel.
  • Why Import Data from Data.gov — Data.gov is a large public repository of government datasets that are commonly used as practice and production data sources for database work. Importing from it mirrors the real ETL (Extract, Transform, Load) work you will do throughout this course.
  • Prerequisites and Tools for the Workflow — This import demonstration assumes a working familiarity with both SQL Server and Microsoft Excel. Each tool plays a specific role in moving XML data into a relational table.
  • Locating and Downloading the XML Dataset — The first step is to find a suitable dataset on Data.gov and download the XML version of the file to your local machine. Reviewing the dataset description before downloading saves rework later.
  • Using Excel as an Intermediate Step — Excel can open an XML file and map its elements into a tabular worksheet, which makes the data far easier to move into SQL Server. This intermediate step also gives you a chance to inspect and clean the data.
  • Importing into SQL Server — With the data flattened and cleaned, you use SQL Server's import tooling to create and populate a destination table. Choosing appropriate data types at this stage prevents errors and simplifies later queries.
  • Troubleshooting Common Import Errors — Import failures are normal and usually trace back to formatting problems in the source data rather than SQL Server itself. Knowing where to look makes resolution quick.

Preparing CSV Flat Files for Import

Covers using Excel to open, inspect, and clean a CSV file so that every cell contains a valid value suitable for a flat-file database import. Demonstrates several common data-cleaning techniques while emphasizing that many valid approaches exist.
  • Why Flat Files Need Preparation Before Import — A CSV flat file is a simple text format where each row is a record and commas separate the fields, but the raw file is rarely ready for a database. The cleanest, easiest import happens when every cell holds a valid value and nothing else.
  • Opening and Inspecting a CSV in Excel — Excel is a convenient tool for reading a CSV file and seeing the shape of the data before it ever touches SQL Server. The first pass is purely diagnostic: understand the columns, the row count, and where the problems live.
  • Handling Blanks, Nulls, and Placeholder Values — Datasets frequently use special markers such as NULL, PrivacySuppressed, N/A, or blanks instead of real numbers. These placeholders must be resolved so the column can be typed consistently.
  • Converting Formulas and Formats to Clean Values — Anything in a cell that is not a plain value — a formula, a currency symbol, a stray space — can confuse the import process. Converting everything to static, correctly typed values makes the flat file predictable.
  • Trimming the File to the Columns You Actually Need — You do not have to import every field in a large public dataset. Reducing the file to the relevant columns shortens the import, simplifies the schema, and lowers the chance of a single bad column failing the whole load.
  • There Are Many Valid Ways to Clean Data — The techniques shown are examples, not a fixed procedure. Different analysts will reach a clean, importable file by different routes, and the test is whether the result loads correctly and preserves meaning.

ETL/ELT Concepts and SQL Server Import Tools

Introduces ETL (or ELT) as the practice of moving data from external sources into your database, a task repeated throughout the course. Explores the most effective import methods and the free integration and import tools available for SQL Server.
  • What ETL (and ELT) Means in Practice — ETL stands for Extract, Transform, Load — the practice of pulling data from an external source, shaping it, and placing it into your database. In this course you will perform some form of ETL (or ELT) nearly every week.
  • Common External Data Sources and File Formats — Public data portals publish datasets in a handful of standard formats, and the format you download determines the import path you take. The course demonstrations use XML and CSV files pulled from government data sites.
  • Importing an XML File into SQL Server — The Lecture 2-1 demonstration walks through pulling an XML file from Data.gov and bringing it into SQL Server. It shows how Excel and XML each serve as a step along the import path.
  • Preparing a CSV Flat File for Import — Flat files rarely arrive clean, so Excel is used to inspect and correct the data before loading. The cleanest import happens when every cell holds a valid value of the expected type.
  • Free Integration and Import Tools for SQL Server — SQL Server ships with and is supported by several no-cost tools for moving data in, and you will use them repeatedly throughout the course. Knowing which tool fits which situation saves considerable time.
  • Choosing the Most Effective Import Method — There is no single best way to import data; the effective choice depends on file size, format, frequency, and how much cleanup is required. The graded discussion asks you to research and defend an answer to exactly this question.
  • Applying ETL in Assignment 2 — Assignment 2 puts these concepts to work by having you create a CollegeDatabase and import College Scorecard statistics into SQL Server. You then query the loaded data and present results in a formatted report.

Querying and Analyzing Imported Data

Applies basic SQL to the imported dataset to identify highest and lowest values, filter non-zero results, and enforce sample-size thresholds. Points to foundational SQL practice resources needed before tackling deeper course material.
  • Purpose of Querying the Imported Data — Once the College Scorecard data is loaded into the CollegeDatabase, the next step is to interrogate it with basic SQL to answer specific questions about student loan debt. The goal is to turn raw imported rows into meaningful comparisons.
  • Identifying Highest and Lowest Values — The core analytical task is ranking institutions by cumulative loan debt and extracting the extremes at each end of the range. This is accomplished with ordering and row-limiting in SQL.
  • Filtering Out Zero and Invalid Results — Raw scorecard data contains zero or missing debt values that would distort a 'lowest' ranking. A WHERE clause is used to exclude these records before ranking.
  • Enforcing a Sample-Size Threshold — Averages computed from very small student populations are statistically unreliable. The analysis therefore restricts results to institutions with a sufficient number of students.
  • Including a Comparison Institution — To give the rankings context, a specific benchmark institution is appended to the result set regardless of where it ranks. This demonstrates how to combine filtered results with targeted lookups.
  • Reporting Query Results Professionally — Analysis is only valuable when communicated clearly, so results must be presented in a readable report rather than raw output. The report shows both the SQL used and the formatted results.
  • Foundational SQL Practice Resources — Students who are not yet comfortable writing SELECT, WHERE, and ORDER BY statements should build those skills before attempting the deeper material later in the course. Several free practice sites are recommended.

Professional Reporting of Database Results

Explains report format expectations: an explanation of the data, a summary of the process, and a description of what the results actually mean. Stresses presenting query output as formatted tables rather than screen captures.
  • Why Report Format Matters — When you work with databases, running the query is only half the job; communicating the results is the other half. A database results report presents your findings in a friendly, easy-to-read format for a reader who did not run the query.
  • The Three Required Report Sections — Every report should contain an explanation of the data, a summary of the process, and a description of the results. These three parts frame the numbers so they can be understood correctly.
  • Explaining the Data and the Process — Before showing numbers, state where the data came from and how it was prepared. This establishes credibility and makes your work reproducible.
  • Describing Results Versus Showing Results — The description of the results is not the results themselves; it is an explanation of what the numbers mean. This distinction is the most commonly missed part of a report.
  • Presenting Query Output as Formatted Tables — Results must be reported as a formatted table, not as a screen capture. Screen captures are not typically acceptable in professional reports.
  • Including the Queries That Produced the Results — A database results report shows the SQL used alongside the output it produced. This lets a reader verify and reproduce your work.

Assignment 2: Import and Analyze College Scorecard Data

Students build a CollegeDatabase in SQL Server, import College Scorecard files, and query cumulative loan debt fields at the 75th and 90th percentiles. The deliverable is a Word or PDF report showing queries, top/bottom ten institutions, and Daytona State College for comparison.
  • Assignment Objective and Deliverable — Assignment 2 asks you to demonstrate that you can import external data into SQL Server and analyze it with basic queries. The deliverable is a written database results report, not a collection of screen captures.
  • Obtaining the College Scorecard Data — The assignment uses U.S. Department of Education College Scorecard data, which is published as downloadable files with an accompanying data dictionary. Two files are provided in the module for the 2015 data set.
  • Importing the Data into SQL Server — Before querying, the raw Scorecard file must be loaded into your CollegeDatabase as a usable table. Use the import techniques demonstrated in the Module 2 lectures.
  • Querying Cumulative Loan Debt Fields — The Scorecard data contains four cumulative loan debt fields: CUML_DEBT_P10, CUML_DEBT_P25, CUML_DEBT_P75, and CUML_DEBT_P90. The report focuses on the 75th and 90th percentile measures.
  • Including Daytona State College for Comparison — Daytona State College serves as a benchmark institution throughout the report. Its debt figures give context to the extreme high and low values in the ranked lists.
  • Writing in Report Format — Professional database work requires presenting query results in a friendly, easy-to-read format. Every report should explain the data, summarize the process, and describe what the results mean.
  • Prerequisite SQL Skills and Support Resources — The assignment assumes comfort with basic SQL SELECT, filtering, sorting, and limiting. If you are not yet comfortable at that level, practice before attempting the queries.
