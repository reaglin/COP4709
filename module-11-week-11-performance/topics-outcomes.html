1. Database Performance Fundamentals and Measurement

Description

Introduces what database performance means across query time, resource utilization, throughput, concurrency and waits, and establishes the golden rule of reducing I/O first. Covers SET STATISTICS IO/TIME and how to interpret logical reads, physical reads and scan counts.

Subtopics

  • What Database Performance Really Means — Database performance measures how quickly and efficiently a database responds to queries, processes transactions, and manages data under real workload conditions. It is never a single number — it is a set of interacting dimensions.
  • The Three Core Performance Metrics — Most performance analysis reduces to three measurable categories: I/O, CPU and waits. Knowing which one dominates tells you where to focus tuning effort.
  • The Golden Rule: Reduce I/O First — The golden rule of SQL Server tuning is to reduce I/O before anything else. Logical and physical reads are the single biggest drivers of slow query performance.
  • Measuring Cost with SET STATISTICS IO and TIME — The quickest way to measure an individual query's resource consumption is to enable statistics output before running it. These two settings give you a reliable baseline for any tuning exercise.
  • Interpreting the STATISTICS IO Output — The STATISTICS IO output lists one row per table touched by the query, with scan count and read counts. Learning to read these numbers is the foundation of all query tuning.
  • Establishing a Baseline Before Tuning — Performance work is only credible when it is measured. A baseline captured before any change is what proves an optimization actually worked.

2. Diagnostic Tools: DMVs, Wait Statistics and Query Store

Description

Explores SQL Server's Dynamic Management Views for finding expensive queries, identifying system bottlenecks through wait types, and monitoring index usage and I/O latency. Includes Query Store for tracking execution plan changes and regressions over time.

Subtopics

  • What Dynamic Management Views Are — Dynamic Management Views (DMVs) are system views that expose SQL Server's real-time internal state, including query execution statistics, index usage, wait types and file I/O. They are the primary diagnostic tool for production performance work because they require no tracing overhead and are always available.
  • Finding the Most Expensive Queries — sys.dm_exec_query_stats holds execution statistics for every plan currently in the plan cache, making it the fastest way to find the worst-performing queries on a server. Cross-applying sys.dm_exec_sql_text retrieves the actual query text for each entry.
  • Wait Statistics: Finding the System Bottleneck — sys.dm_os_wait_stats records what SQL Server has been waiting on, revealing the system-level bottleneck rather than symptoms in individual queries. Running it when the system feels slow quickly points tuning effort in the right direction.
  • Monitoring Index Usage and Missing Indexes — Index-related DMVs show both the indexes SQL Server wishes existed and the ones that are costing writes without being read. Together they keep an indexing scheme lean and targeted.
  • Diagnosing Disk I/O Latency — sys.dm_io_virtual_file_stats reports read and write latency for every individual database file, isolating storage problems from query problems. It is the natural follow-up when PAGEIOLATCH waits dominate the wait statistics.
  • Query Store: Tracking Plan Changes and Regressions — Query Store (SQL Server 2016 and later) persists execution plans and runtime statistics in the database itself, so plan history survives restarts and cache flushes. It makes it possible to prove exactly when a plan changed and caused a regression.

3. Reading and Interpreting Execution Plans

Description

Explains how the query optimizer builds execution plans and how to view estimated versus actual plans. Covers key plan operators such as index seeks, scans, key lookups and join types, plus the warning signs that reveal tuning opportunities.

Subtopics

  • What an Execution Plan Is — An execution plan is SQL Server's step-by-step blueprint for how it will retrieve and process the data a query asks for. It is the foundation of all query tuning work.
  • Estimated vs Actual Execution Plans — SQL Server can show the plan it intends to use without running the query, or the plan it actually used along with real row counts. Comparing the two is a core diagnostic technique.
  • Data Access Operators — Seeks, Scans and Lookups — The operators that touch base data are usually where the I/O cost lives, so they are the first things to identify in any plan.
  • Join and Supporting Operators — The plan also shows how SQL Server combines row sets and what extra work it performs, such as sorting or spooling intermediate results.
  • Warning Signs That Reveal Tuning Opportunities — Certain visual and numeric cues in a plan point straight at the fix. Scanning for these red flags is faster than reading every operator in detail.
  • Query Store — Tracking Plan Changes Over Time — A single plan capture is a snapshot; Query Store (SQL Server 2016+) persists plans and runtime statistics so you can see when a plan changed and performance regressed.

4. Index Types and Structures

Description

Details clustered, non-clustered, covering, filtered, columnstore and unique indexes, including their structure, limits and ideal use cases. Provides T-SQL syntax for creating each type and guidance on composite key ordering and INCLUDE columns.

Subtopics

  • What an Index Is and Why Structure Matters — An index is a separate data structure SQL Server maintains alongside a table so rows can be located without scanning every page. The textbook analogy applies: you look up the term in the index to find the page rather than reading every page.
  • Clustered Index — The Table Itself — A clustered index defines the physical storage order of the rows, which means the table *is* the clustered index. Only one clustered index is permitted per table.
  • Non-Clustered Indexes and Composite Key Order — A non-clustered index is a separate B-tree containing the key columns plus a row locator pointing back to the base table. SQL Server allows up to 999 non-clustered indexes per table.
  • Covering Indexes with INCLUDE — A covering index contains every column a query needs, so SQL Server never returns to the base table. INCLUDE adds non-key columns to the leaf level of a non-clustered index.
  • Filtered Indexes for Partial-Table Queries — A filtered index indexes only the rows that match a WHERE predicate, producing a smaller and more targeted structure. It is ideal where queries repeatedly target a subset such as active or open records.
  • Columnstore Indexes for Analytics — A columnstore index stores data column-by-column instead of row-by-row, giving 10–100× compression and enabling batch mode execution. It is designed for analytical queries aggregating a few columns across millions of rows.
  • Unique Indexes and Index Type Selection — A unique index enforces uniqueness as a database-level constraint while also providing a fast lookup path. Selecting among the index types is a trade-off between read benefit, storage and write overhead.

5. Index Management, Trade-offs and Maintenance

Description

Weighs the read benefits of indexes against write overhead, storage cost and fragmentation. Covers finding missing and unused indexes through DMVs, evaluating optimizer recommendations critically, and applying REORGANIZE versus REBUILD maintenance strategies.

Subtopics

  • The Read/Write Trade-off of Indexes — Indexes accelerate reads but every index must be maintained on every data modification. Index design is therefore a balancing act between query speed and write throughput.
  • Finding Missing Indexes with DMVs — SQL Server records every occasion where the optimizer wished an index existed, exposing these through the missing index DMVs. They provide fast wins but must be read critically.
  • Evaluating Optimizer Recommendations Critically — Missing index recommendations are generated greedily — the optimizer evaluates each query in isolation without knowing about existing or other suggested indexes. Blindly creating them all is a common anti-pattern.
  • Identifying and Removing Unused Indexes — An index that is never seeked or scanned still costs storage and write overhead on every modification. sys.dm_db_index_usage_stats reveals these pure-cost indexes.
  • Index Fragmentation and Its Impact — Over time INSERTs and UPDATEs cause page splits, leaving pages partially full and out of logical order. Fragmented indexes force SQL Server to read more pages to return the same data.
  • REORGANIZE versus REBUILD Maintenance Strategy — SQL Server offers two defragmentation operations with different cost and thoroughness profiles, chosen according to measured fragmentation level.
  • Keeping Statistics Current — Index maintenance is incomplete without accurate statistics, because the optimizer relies on column histograms to estimate row counts and choose plans.

6. Query Optimization Techniques

Description

Focuses on writing efficient SQL through SARGable predicates, avoiding SELECT *, choosing EXISTS over IN, and preventing implicit type conversions. Also explains how the optimizer uses statistics and when to update them.

Subtopics

  • Query Structure Drives Cost — Many performance problems stem from how a query is written rather than from a missing index. The same logical result can be expressed in several ways, each with very different execution costs.
  • SARGability — Writing Index-Friendly Predicates — A condition is SARGable (Search ARGument able) when SQL Server can evaluate it with an index seek. Non-SARGable conditions force index scans or full table scans.
  • Avoiding SELECT * — SELECT * retrieves every column in the table, including ones the application never uses. This wastes I/O, memory, and network bandwidth, and it undermines covering indexes.
  • EXISTS vs IN vs JOIN for Existence Checks — When a query only needs to know whether a related row exists, the choice of construct affects how much work the engine performs. EXISTS is usually the most efficient option for existence tests.
  • Preventing Implicit Type Conversions — When a WHERE clause compares columns of different data types, SQL Server converts one side to match the other. That conversion is applied to every row and prevents index seeks.
  • Statistics — What the Optimizer Uses to Estimate Cost — SQL Server statistics are histograms describing the distribution of values in a column. The optimizer uses them to estimate how many rows a predicate will return, and stale statistics lead to poor plan choices.
  • Query-Writing Best Practices and Anti-Patterns — A short checklist captures the habits that keep queries efficient and highlights the patterns that repeatedly cause slow performance.

7. Normalization, Denormalization and Schema Design for Performance

Description

Compares normalized 3NF designs for OLTP write-heavy workloads against denormalization techniques such as redundant columns, summary tables and star schemas for read-heavy analytics. Introduces indexed views as a way to gain denormalized speed while retaining normalized base tables.

Subtopics

  • Normalization (3NF) and Write Performance — Normalization organizes tables so each piece of information is stored exactly once, which is ideal for OLTP systems with heavy INSERT, UPDATE and DELETE activity. A 3NF design such as separate customers, products, orders and order_items tables keeps each concept in a single place.
  • The Read Cost of Highly Normalized Schemas — The trade-off for normalization is that reporting and analytical queries must reassemble data across many tables. Every JOIN adds CPU, memory and I/O cost through hash builds, loop iterations or merge operations.
  • Denormalization as a Deliberate Design Decision — Denormalization intentionally introduces redundancy to reduce the number of JOINs required by frequently executed queries. It trades write complexity and the risk of anomalies for faster reads, and should only follow a measured performance problem.
  • Technique 1 — Redundant and Derived Columns — The simplest denormalization adds a column that could otherwise be obtained through a JOIN, so hot queries avoid the JOIN entirely. For example, storing customer_name directly on the orders table.
  • Technique 2 — Pre-Aggregated Summary Tables — A summary table stores pre-computed aggregates that are refreshed by triggers or scheduled jobs, so dashboards read a small table instead of aggregating millions of rows on demand.
  • Technique 3 — Flattened Reporting Tables and Star Schemas — Data warehouses store dimension attributes directly in a wide fact table or a single wide dimension, eliminating multi-hop JOINs for standard reports. This structure also suits columnstore indexes and batch-mode execution.
  • Indexed Views — Normalized Base, Denormalized Speed — An indexed view (a materialized view in other platforms) physically stores a view's result set and lets SQL Server maintain it automatically. You keep normalized base tables while gaining denormalized read performance.
  • Choosing the Right Approach for the Workload — Schema design for performance is about matching the structure to the dominant workload. Use this decision guide when selecting between normalization, denormalization and hybrid approaches.

8. Advanced Techniques and the Tuning Workflow

Description

Covers partitioning for large time-series tables, temp tables versus CTEs and table variables, and stored procedure plan reuse. Concludes with the seven-step tuning workflow, best practice checklists and common anti-patterns to avoid.

Subtopics

  • Table Partitioning for Large Time-Series Tables — Table partitioning physically divides a very large table into smaller segments based on a column value, most commonly a date. Queries that target a date range then read only the relevant segments instead of the whole table.
  • Temp Tables for Staging Complex Multi-Step Logic — A temp table (#temp) is stored in tempdb, automatically gets statistics, and can be indexed. This makes it ideal for intermediate results that are queried or joined more than once.
  • CTEs, Subqueries and Table Variables Compared — Not every intermediate result needs materialising. Subqueries, CTEs, temp tables and table variables differ in whether they are materialized and whether the optimizer has statistics for them.
  • Stored Procedures, Plan Caching and SET NOCOUNT ON — Stored procedures compile their execution plan once and cache it, so subsequent calls reuse the plan without recompilation overhead. This makes them an efficient way to run repeated parameterised workloads.
  • The Seven-Step Performance Tuning Workflow — Effective tuning is a repeatable, evidence-driven cycle rather than guesswork. The workflow moves from identifying a problem query through to monitoring the fix under real workload.
  • Best Practice Checklists — Indexing, Queries and Schema — Consolidated checklists give a practical set of defaults to apply across indexing, query writing and schema design. They capture the habits that prevent most performance problems before they appear.
  • Common Anti-Patterns to Avoid — A handful of recurring mistakes account for a large share of production performance problems. Recognising them quickly shortens the diagnosis phase of the tuning workflow.
