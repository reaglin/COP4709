Aggregation Fundamentals in SQL

Introduces aggregation as the process of collapsing many rows into a single summary value, and previews the core functions (COUNT, SUM, AVG, MIN, MAX, COUNT DISTINCT) along with the general syntax pattern and the bookstore sample dataset used throughout.
  • What Aggregation Means — Aggregation in SQL performs a calculation across a set of rows to produce a single summary value. Rather than returning every individual record, aggregate functions collapse many rows into meaningful totals, counts, and averages.
  • The Core Aggregate Functions — Six functions handle the vast majority of aggregation work in SQL. Each is supported by every major database system including Oracle, SQL Server, MySQL, PostgreSQL, and IBM Db2.
  • The General Syntax Pattern — Every aggregation query follows the same predictable clause skeleton. Mastering this template makes complex reporting queries straightforward to construct.
  • Supporting Tools You Will Use — Three companion keywords make aggregation practical and readable. They are introduced here and explored in depth later in the guide.
  • The Bookstore Sample Dataset — All examples throughout this guide use a single orders table from a fictional online bookstore. Working from one consistent dataset makes it easy to compare how each function behaves.

Core Aggregate Functions: COUNT, SUM, and AVG

Explores counting rows versus non-NULL and distinct values, totalling numeric columns, and calculating averages with rounding. Highlights NULL-handling traps such as COUNT(*) vs COUNT(column) and SUM returning NULL on empty result sets.
  • COUNT(*) — Counting Every Row — COUNT(*) returns the total number of rows that match a query, regardless of whether any column contains NULL values. It is the safest choice when the question is simply "how many records?"
  • COUNT(column) — Counting Non-NULL Values — COUNT(column) counts only the rows where the named column holds a value that is not NULL. This makes it a quick way to measure data completeness.
  • COUNT(DISTINCT column) — Counting Unique Values — COUNT(DISTINCT column) returns the number of unique, non-NULL values in a column rather than the number of rows. It answers questions about variety rather than volume.
  • The COUNT(*) vs COUNT(column) Trap — The most common reporting error with COUNT is assuming the two forms are interchangeable. When a column contains NULLs, they return different numbers.
  • SUM() — Totalling Numeric Values — SUM() adds up all non-NULL values in a numeric column to produce a single total. It is the workhorse function for revenue, quantity, and other additive measures.
  • SUM Returns NULL on Empty Result Sets — When no rows match the query, SUM() returns NULL rather than 0. Applications that expect a number can break or display blanks because of this.
  • AVG() — Calculating and Rounding Averages — AVG() returns the arithmetic mean of the non-NULL values in a numeric column, equivalent to SUM(col) / COUNT(col). Because raw averages carry many decimal places, ROUND() is usually applied for presentation.

MIN, MAX, and Combined Summary Queries

Covers finding extreme values across numbers, dates, and strings, including alphabetical and chronological behaviour. Demonstrates combining all five core aggregates into a single comprehensive summary query.
  • What MIN() and MAX() Do — MIN() and MAX() return the smallest and largest values found in a column across the rows the query examines. Unlike SUM() and AVG(), they are not limited to numeric data.
  • MIN and MAX on Numeric Columns — On numeric columns, MIN() and MAX() identify the lowest and highest values, making them ideal for finding price floors, ceilings, and value ranges.
  • MIN and MAX on Date Columns — When applied to a DATE column, MIN() returns the earliest date and MAX() returns the most recent — a chronological rather than numeric comparison.
  • MIN and MAX on String Columns — On text columns, MIN() and MAX() compare values alphabetically rather than numerically, returning the first and last entries in sort order.
  • Using MIN and MAX to Satisfy the GROUP BY Rule — MIN() and MAX() are often used to legally include an otherwise ungrouped column in a grouped query.
  • Combining All Five Core Aggregates — COUNT, SUM, AVG, MIN, and MAX can all appear in a single SELECT list to produce one comprehensive summary row.

Column Aliases with AS

Explains how AS produces readable, referenceable output column names for aggregates and calculated expressions, including quoting rules and table aliases. Clarifies why aliases cannot be referenced in a WHERE clause.
  • What a Column Alias Does — AS creates a column alias — a custom label applied to a column or expression in your query results. It changes only the output header, not the stored data.
  • AS Syntax and Quoting Rules — The AS keyword is technically optional, but explicit use makes queries far easier to read. Quoting lets you create aliases containing spaces or special characters.
  • Aliasing Calculated and Derived Columns — Aliases are most valuable when the SELECT list contains arithmetic, nested functions, or CASE expressions. They turn an unreadable formula into a business-meaningful column name.
  • Table Aliases — AS also works on table names, creating a short handle used to qualify columns. This is essential for readability in multi-table joins.
  • Why Aliases Fail in WHERE — Because WHERE is evaluated before SELECT in SQL's logical execution order, an alias defined in SELECT does not yet exist when WHERE runs. Referencing it produces an unknown-column error.
  • Where Aliases CAN Be Used — Not every clause rejects aliases. Clauses evaluated after SELECT can reference the names you defined there.

GROUP BY — Aggregating by Category

Shows how GROUP BY splits rows into groups for per-group aggregation across single columns, multiple columns, and date expressions for time-series reporting. Establishes the golden rule that every selected column must be grouped or aggregated.
  • What GROUP BY Does — GROUP BY splits the rows returned by a query into groups based on one or more columns, then applies each aggregate function separately to every group. Without GROUP BY, aggregate functions collapse the entire table into a single summary row.
  • GROUP BY a Single Column — The most common pattern groups by one descriptive column and aggregates one or more numeric columns alongside it. The grouping column appears in SELECT so each summary row is labelled.
  • GROUP BY Multiple Columns — Listing more than one column in GROUP BY creates finer-grained groups — one output row for every unique combination of the listed values. This supports cross-tab style breakdowns.
  • The Golden Rule of GROUP BY — Every column in the SELECT list must either appear in the GROUP BY clause or be wrapped in an aggregate function. Violating this rule produces undefined results or an outright error in strict mode.
  • GROUP BY with Date Functions for Time-Series Reports — You can group by an expression, not just a raw column. Applying YEAR() and MONTH() to a date column is the standard way to build monthly or yearly trend reports.
  • Combining GROUP BY with Other Clauses — GROUP BY sits in a fixed position in the query, between WHERE and HAVING, and works together with aliases and sorting to produce a finished report.

HAVING — Filtering Aggregated Results

Contrasts WHERE (row-level filtering before grouping) with HAVING (group-level filtering after aggregation) and demonstrates using both together. Includes practical patterns such as HAVING COUNT(*) to isolate active groups.
  • What HAVING Does — HAVING filters groups after aggregation has been performed, making it the GROUP BY equivalent of WHERE. It allows conditions to be written against aggregate expressions such as SUM(total) or COUNT(*).
  • WHERE vs HAVING — Side by Side — WHERE filters individual rows before grouping; HAVING filters resulting groups after grouping. Choosing the wrong clause is one of the most common aggregation errors.
  • A Basic HAVING Query — The simplest HAVING pattern groups rows by a category column and keeps only the groups whose aggregate value crosses a threshold.
  • Using WHERE and HAVING Together — The two clauses are complementary and frequently appear in the same query: WHERE narrows the rows, then HAVING narrows the groups built from those rows.
  • HAVING COUNT(*) — Finding Active Groups — A classic business pattern uses HAVING COUNT(*) to isolate groups with enough activity, such as repeat customers or courses with sufficient enrollment.
  • Execution Order Explains Why HAVING Exists — SQL evaluates clauses in a logical order — FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY — and this order explains why aggregate filtering needs its own clause.

Advanced and Vendor-Specific Aggregate Functions

Surveys COUNT(DISTINCT) within groups, text aggregation with GROUP_CONCAT and STRING_AGG, statistical functions like STDDEV and VARIANCE, and subtotal generation with WITH ROLLUP, noting differences across Oracle, SQL Server, MySQL, PostgreSQL, and Db2.
  • COUNT(DISTINCT) Within Groups — COUNT(DISTINCT column) counts only unique, non-NULL values, and becomes especially powerful when combined with GROUP BY to measure reach rather than volume.
  • Text Aggregation: GROUP_CONCAT and STRING_AGG — These vendor-specific functions concatenate string values from many rows in a group into a single delimited text column, producing readable summary lists.
  • Statistical Aggregates: STDDEV and VARIANCE — STDDEV and VARIANCE measure how spread out numeric values are around their mean, letting you judge consistency rather than just magnitude.
  • Subtotals and Grand Totals with ROLLUP — ROLLUP extends GROUP BY by automatically generating subtotal and grand total rows beneath the detail rows, which is ideal for financial and management reports.
  • Vendor Support Varies Across Database Systems — Beyond the five core aggregates, support for advanced functions differs sharply between Oracle, SQL Server, MySQL, PostgreSQL and IBM Db2, so always check your platform's documentation.

Query Execution Order, Real-World Patterns, and Best Practices

  • The Six-Step Logical Execution Order — SQL does not evaluate a query in the order you write it. Understanding the logical execution order explains alias rules, filtering behaviour, and why HAVING exists as a separate clause from WHERE.

  • Healthcare and University Patterns with SUM(CASE WHEN …) — Conditional aggregation lets you count rows matching a specific condition inside a grouped query without writing a subquery.
  • Best Practices for Aggregation Queries — A few habits make aggregation queries readable, maintainable, and efficient in production reporting.
